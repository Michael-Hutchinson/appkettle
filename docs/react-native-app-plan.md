# React Native app — plan

A standalone Android (and later iOS) phone app that replaces the dead AppKettle
vendor app. Talks to the kettle directly over the LAN — does **not** depend on
the eventual Raspberry Pi, since the kettle's protocol is local-only TCP.

This document is the spec. Read it cold and you should be able to start coding.

---

## Context for the next session

If you're picking this up fresh:

- The target hardware is the **AppKettle** smart kettle from iFavine. The
  vendor and their cloud (`jingxuncloud`) are defunct. The kettle still works
  locally on TCP/6002 using a custom protocol they call "Across" — reverse-
  engineered from the official Android APK earlier in this project.
- The Node-side bridge already exists in this repo (`appkettle`) — protocol
  library, TCP client, UDP discovery, MCP servers (stdio + HTTP), CLI. All
  tested, CI'd, working in production against a real kettle.
- The phone app is a **separate project** in a **new repo** (`appkettle-app`).
  This plan is what that session should follow.
- The kettle's IMEI and LAN IP are discovered at runtime via UDP broadcast
  (don't hard-code them — DHCP can reassign the IP, and IMEI is per-device).
- Stack chosen as React Native (single codebase for both platforms; JS/React
  expertise already in the project).

### Decisions already made

| Decision         | Choice                            | Why                                                 |
| ---------------- | --------------------------------- | --------------------------------------------------- |
| Stack            | React Native                      | User is a JS/React dev; iOS+Android in one codebase |

| UI library       | None for V1                       | Built-in RN components are enough                   |

- Theme: dark/light/system (system default proposed)

## Architecture

The RN app is layered the same way as the Node side:

```
┌─────────────────────────────────────────┐
│ App.tsx, MainScreen.tsx                 │  React UI
│ components/StatusCard, BoilButton, ...  │
├─────────────────────────────────────────┤
│ hooks/useKettle.ts                      │  React state ↔ kettle bridge
├─────────────────────────────────────────┤
│ kettle/client.ts                        │  TCP connection, send/receive,
│ kettle/discovery.ts                     │  UDP probe (reused, ported)
├─────────────────────────────────────────┤
│ protocol/                               │  PURE — copies straight from the
│   hex.ts, frames.ts, commands.ts,       │  Node repo with zero changes
│   parsers.ts, index.ts                  │
└─────────────────────────────────────────┘
```

The bottom layer (`protocol/`) is pure functions over strings and Buffers. RN
ships a `Buffer` polyfill via `react-native-buffer` (or it's available on the
global if Hermes is enabled, which it is by default in RN ≥ 0.72). Everything
in `protocol/` works unchanged.

The middle layer (`kettle/`) is a mechanical port of `src/client.ts` and
`src/discovery.ts` from this repo — same logic, different I/O primitives:

| Node primitive                   | RN replacement                                                     |
| -------------------------------- | ------------------------------------------------------------------ |
| `import net from "node:net"`     | `import TcpSocket from "react-native-tcp-socket"`                  |
| `import dgram from "node:dgram"` | `import dgram from "react-native-udp"`                             |
| `EventEmitter` (typed)           | `EventEmitter` from `events` polyfill, or rebuild as Zustand store |
| `Buffer.alloc / Buffer.concat`   | Same — `Buffer` polyfill works                                     |
| `process.env.X`                  | `Config` from `react-native-config` (later); hardcode for V1       |

The top layer is React. A single `useKettle()` hook owns the connection and
exposes `{ status, isConnected, boil, stop, error }`.

**Versions are intentionally fuzzy** — use whatever's current at start time.
Native modules in RN move fast; pinning specific patch versions in this doc

### Why these libraries

- **`react-native-tcp-socket`** — the only mature library for raw TCP in RN.
  API is similar to `node:net` (createConnection, write, on('data'), etc.) so
  the port from `client.ts` is mostly mechanical.
- **`react-native-udp`** — mature, parallel to `node:dgram`. Discovery uses
  this.
- **`buffer`** — explicit polyfill for the `Buffer` global. Hermes provides it
  by default in modern RN, but importing explicitly avoids surprises.
- **`async-storage`** — persist the kettle's IP and IMEI between app launches
  so we don't re-discover every cold start.

### Permissions

Android needs these in `AndroidManifest.xml`:

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
<uses-permission android:name="android.permission.ACCESS_WIFI_STATE" />
<uses-permission android:name="android.permission.CHANGE_WIFI_MULTICAST_STATE" />
```

That last one is the gotcha — without `CHANGE_WIFI_MULTICAST_STATE`, UDP
broadcasts (the discovery probe) silently fail to be received on Android.

iOS later will need the **Local Network** entitlement plus
`NSLocalNetworkUsageDescription` in `Info.plist`.

## Protocol crash-course (from the Node implementation)

Read this in detail; it's the source of the most likely bugs in the port.

### Wire format

```
Outer:   ##00<2-hex-len>{json}&&
JSON:    {"app_cmd":"62","imei":"<imei>","SubDev":"","data2":"<across-hex>"}
Across:  AA + frameLen(4) + prefix(4) + msgUnique(12) + serial(2)
       + api(2) + retain(4) + content + sign(2)
```

- **Outer envelope** — 4-byte length header (`##00<2-hex-len>` where len is
  the length of the JSON body in hex), then the JSON, then `&&` terminator.
- **Inner JSON** — `app_cmd` is always `62` for our purposes. `imei` is the
  kettle's identifier (parsed from discovery). `data2` is the Across binary
  frame as ASCII hex.
- **Across frame** — starts with `0xAA`, then framelen (2 bytes, hex-encoded
  as 4 chars), prefix (`0000` for operational, `0100` for setup), 12-byte
  message UUID, 1-byte serial, 1-byte API code, 4-byte retain (always `0000`),
  variable content, 1-byte XOR-of-sum checksum.

### Byte stuffing — easy to get wrong

Any literal `0xAA` byte that appears inside the Across frame's content (not
the leading header) gets escaped to `AA55`. The receiver un-stuffs by reading
left to right: `AA` followed by `55` collapses to a single `AA`; `AA` followed
by anything else is a literal `AA` byte.

This is the most likely place to get the port wrong. The existing
`src/protocol/hex.ts` has correct `stuff()` and `unstuff()` functions —
copy them verbatim and trust them. There are unit tests in
`src/protocol.test.ts` proving they round-trip.

### Replies use `data3`, not `data2`

Outbound: `{"data2": "..."}`. Inbound: `{"data3": "..."}`. The same Across
frame format inside, just a different JSON key. `extractData3()` in
`src/protocol/frames.ts` handles this.

### Keep-alive

After connecting, the client must send a literal string `##000bKeepConnect&&`
every ~25 seconds, otherwise the kettle drops the connection. The first
keep-alive should fire **immediately after** TCP connect succeeds, before any
real command. The Node `client.ts` does this in the `sock.on("connect")`
handler.

### The "first frame is the ready signal"

After the keep-alive is sent, the kettle responds with an INIT-ish frame
(usually API code `A4`). The Node client treats the first inbound frame as
the "ready" signal — only after that should commands be sent. The RN client
should mirror this: don't fire `boil()` until the first reply lands.

### The auto-wake gotcha

The kettle returns `ack=00` (rejection) to `SET_START_BOIL` (API `39`) when
it's been idle in `Standby` state. The fix the Node client uses: before
sending boil, check the cached state — if it's not `Heating` or `Keep Warm`,
send `SET_KETTLE_ON` (API `41`) first. Mirror this in the RN port.

If you skip this, the user will tap "Boil" from Standby and get a
mysterious-looking error. Don't.

### Kettle states

```ts
const KETTLE_STATES = [
  "Not on base", // 0 — kettle physically off the base
  "TBD", // 1 — unknown / unused
  "Standby", // 2 — on base, idle, display off
  "Ready", // 3 — boil completed, water hot
  "Heating", // 4 — actively heating
  "Keep Warm", // 5 — maintaining target temp
];
```

The client code derives `power: ON | OFF` from these (`Heating` and
`Keep Warm` are ON; everything else is OFF).

### Discovery

UDP broadcast on **port 15103**. Probe payload:

```
Probe#YYYY-MM-DD-HH-MM-SS-1
```

Sent every 1.5s for up to 6 attempts, to `255.255.255.255` and to every
non-loopback interface's broadcast address. The kettle replies (also on 15103) with a `#`-delimited string; field 0 is the IMEI, field 6 is JSON
metadata including `AP_ssid`, `devRouter`, `deviceStatus`. The client
captures `rinfo.address` from the reply for the kettle's IP.

The Node implementation is `src/discovery.ts`. The RN port is structurally
identical — just `react-native-udp` instead of `node:dgram` and the
`os.networkInterfaces()` lookup needs to use `react-native-network-info`
or be omitted (broadcast to `255.255.255.255` only is usually enough).

## MVP (V1)

### Single screen, three controls

```
┌─────────────────────────────────┐
│  appkettle                  ⓘ   │
│                                 │
│  ┌───────────────────────────┐  │
│  │   Standby                 │  │
│  │   97°C   ───►   100°C     │  │
│  │   351 ml                  │  │
│  │   updated 3s ago          │  │
│  └───────────────────────────┘  │
│                                 │
│  ┌───────────┐  ┌───────────┐   │
│  │   Boil    │  │   Stop    │   │
│  └───────────┘  └───────────┘   │
│                                 │
│  ● connected to <your-kettle-ip>   │
└─────────────────────────────────┘
```

- **Status card** — refreshes from the heartbeat stream (`status` events from
  the client). Shows state, current temp, target temp, volume, last-update
  age in a friendly format.
- **Boil button** — tap = boil to 100°C. Long-press = open temp picker
  (40-100°C in 5° increments). Disabled while `state === "Heating"`.
- **Stop button** — disabled unless `state === "Heating"` or `state === "Keep Warm"`.
- **Connection banner** — bottom of screen. Shows current connection state.
  Hidden when connected and last update is recent.

### Lifecycle

- **App foreground** → check AsyncStorage for cached `{ip, imei}`. If
  present, try to connect. If connect fails OR no cached config, run
  discovery. If discovery succeeds, save `{ip, imei}` to AsyncStorage and
  connect. If discovery fails, show "kettle not found" with a manual IP
  entry option.
- **App background** → close TCP socket cleanly. Don't try to keep it alive
  (battery + Android will kill it anyway).
- **Status update event** → set state, re-render.
- **Connection drop** → show banner, retry with backoff (start 1s, double
  to 30s — same logic as the Node client).

### `useKettle()` hook sketch

```ts
type KettleState = {
  status: KettleStatus | null;
  isConnected: boolean;
  isConnecting: boolean;
  error: string | null;
};

type KettleActions = {
  boil: (temp?: number) => Promise<void>;
  stop: () => Promise<void>;
  rediscover: () => Promise<void>;
};

export const useKettle = (): KettleState & KettleActions => {
  // ...returns merged state + actions
};
```

The hook owns a `KettleClient` instance internally, subscribes to its events,
and exposes a clean API to React components. AppState listener handles
foreground/background transitions.

## Sideload pipeline (Android)

### One-time setup

1. **Install JDK 17+** and **Android Studio** (or just the SDK + platform tools).
2. **Generate a release signing key**:

   ```bash
   keytool -genkeypair -v -storetype PKCS12 \
     -keystore appkettle-release.keystore \
     -alias appkettle \
     -keyalg RSA -keysize 2048 -validity 10000
   ```

   Save the keystore + password securely (1Password / similar). If lost, you
   can never push an update — every install is treated as a different app.

3. **Configure `android/app/build.gradle`** with the signing config (RN docs
   have the exact pattern).

### Per-iteration

For dev:

```bash
# Phone in dev mode, USB-connected, USB debugging on
npx react-native run-android  # debug build, hot reload
```

For shipping a release APK:

```bash
cd android
./gradlew assembleRelease
# APK at android/app/build/outputs/apk/release/app-release.apk
```

Transfer that APK to the phone (USB / Drive / Signal / KDE Connect / whatever)
and tap to install. Android prompts to allow installs from this source the
first time.

### Distribution to others

Just send them the APK. They tap to install. No special handling needed.

## Implementation order

This is the order to attack it in the eventual session. Each step is
independently testable on the phone:

1. **Init**: `npx @react-native-community/cli init appkettle-app --skip-git-init`,
   then `git init`, push to a new GitHub repo (private). Verify hello-world
   runs on your phone via `run-android`.
2. **Copy `protocol/`**: copy the five files from this repo's
   `src/protocol/`. Add `import { Buffer } from "buffer"` to the top of any
   file that uses Buffer (or rely on the polyfill if Hermes provides it).
   Run a quick sanity test with a hand-crafted hex string just to confirm
   `parseStatus` parses on RN.
3. **Port `client.ts`**: copy and rewrite the imports. Use
   `react-native-tcp-socket`'s connect/write/on('data') API. Replace the
   typed EventEmitter with a callback-based pattern OR `events` polyfill.
   Keep the same public methods: `connect()`, `boil()`, `stop()`,
   `pollStatus()`, `getCachedStatus()`. Keep the auto-wake logic in `boil()`.
4. **Port `discovery.ts`**: same shape with `react-native-udp`. Drop the
   `os.networkInterfaces()` enumeration; broadcast to `255.255.255.255` only.
5. **`useKettle` hook**: lifecycle + state. Wire AppState listener for
   foreground/background. Test in a stub component that just dumps the
   status JSON to the screen.
6. **UI**: status card + buttons + banner. Theme-aware colours. No fancy
   animations.
7. **AsyncStorage**: persist `{ip, imei}` after first successful connect.
8. **Release APK**: signing key, gradle build, install on the phone.
9. **Use it for a few days**. Note what's missing or annoying. Plan V2.

### Cold-test pattern

The Node integration tests use a loopback `net.createServer()` that mimics
the kettle (see `src/client.integration.test.ts`). The same pattern works in
Jest if you want unit-test coverage on the RN port — just use Node's `net`
in the test environment (Jest runs on Node, not RN's runtime).

## Common pitfalls

Things that will trip up the port if you don't watch for them:

- **`Buffer` behaviour differs subtly**. The polyfill is mostly compatible
  but some methods missing. Test `Buffer.from(s, "utf8").toString("hex")`
  early — that's used by `strToHex` and is the most-load-bearing buffer op
  in the protocol.
- **Byte stuffing**. Don't reimplement `stuff()` / `unstuff()`; copy them.
- **Big-endian vs little-endian** is irrelevant — every multi-byte number
  in the protocol is hex-encoded as ASCII, so endianness never enters the
  picture. (Mentioned because it's the first thing a network programmer
  worries about.)
- **TCP message framing**. `react-native-tcp-socket` delivers data in
  arbitrary chunks just like Node — don't assume one `data` event = one
  message. The Node client uses `Buffer.concat` + `indexOf("&&")` to find
  frame boundaries; mirror that exactly.
- **Permissions**. Forgetting `CHANGE_WIFI_MULTICAST_STATE` makes UDP
  discovery silently fail on Android.
- **AppState transitions**. Without proper background cleanup, the TCP
  socket leaks across app suspends. Test by force-killing the app and
  re-opening; the connection should re-establish cleanly.
- **iOS NSLocalNetworkUsageDescription**. Not relevant for V1, but iOS
  refuses to even _broadcast_ without it. Don't forget when you bring iOS
  online.
